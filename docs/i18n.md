# Internationalisation

Every request is served in a locale resolved from the request itself.
Framework and host strings translate through one `Translator`; dates
and decimals format in the browser. English ships built in; French and
Russian ship as gettext catalogs.

## What is translated, and what is not

Translated, wherever it appears in a page:

- Framework text — button labels, page titles, confirmation dialogs,
  filter labels, accessible names (`aria-label`, `placeholder`,
  `title`, `alt`), flash messages, validation errors, error pages.
- Host-declared text rendered through the framework's own templates —
  a field's `label`/`help_text`/`placeholder`, a `Fieldset`'s `title`/
  `description`, a `Filter`'s label and choice labels, an `Action`'s
  label and confirm text, an `Inline`'s label, a custom page's nav
  label, a dashboard widget's title, the site title.

Never translated:

- Record values — whatever your `ModelAdmin` returns as field data.
- Object labels (breadcrumbs, relation links), email addresses, IDs,
  `Principal.display_name`.
- Table cells, chart points, activity/timeline entries — any widget
  data.
- Locale names in the switcher ("English", "Français", "Русский" are
  never run through the translator).

## Configuration

All optional; the defaults serve English plus every catalog the
framework ships, resolved per request, switcher shown:

```python
admin = Admin(
    model_admins=[...],
    default_locale="en",            # default "en"
    locales=["en", "fr"],           # restrict; default = every locale with a catalog
    locale_resolver=lambda request, principal: ...,
    catalogs=[("locales", "myapp")],   # host catalogs, layered over the framework's
    translator=my_translator,       # replace the default Translator entirely
    locale_names={"de": "Deutsch"},
    locale_switcher=True,           # False hides the switcher, unmounts its route
    pseudo_locale=False,            # dev/test only: True enables "en-XA"
)
```

`en` needs no catalog: its message *is* the English text. The
supported set is `en` plus every locale with a framework or host
catalog, intersected with `locales` when given, plus `en-XA` when
`pseudo_locale` is set. `translator` replaces the default
catalog-backed `GettextTranslator` outright — pair it with `locales`,
since the admin can no longer ask a foreign translator what it
supports.

## How a request's locale is chosen

Resolved once per request, before any handler runs. First match wins:

1. The switcher cookie, `admin_locale` — the visitor's most recent
   explicit choice, if it still names a supported locale.
2. `locale_resolver(request, principal)`, if configured. `principal`
   is `None` on the login and error pages, since nothing is
   authenticated there yet; it's `None` everywhere else too, when no
   `authenticator` is configured. An empty or unsupported result falls
   through to the next step. Authentication happens at most once per
   request even when both the locale resolver and the route's own
   authorization need the principal — the second lookup reuses the
   first's result. See [`authentication.md`](authentication.md).
3. `Accept-Language`, best match against the supported set, honouring
   q-values.
4. `default_locale`.

Every candidate from steps 1–3 is matched the same way: an exact
locale wins, otherwise a regional variant maps onto its base language
(`fr-CA` → `fr`), and one language is never mapped onto another. The
pseudo-locale is never matched from `Accept-Language` — it has to be
chosen explicitly, by cookie or resolver.

The resolved locale drives everything in the request: the page and any
htmx fragment, flash messages set during it, validation errors, error
pages, `<html lang>`, and export column headers.

## The language switcher

A dropdown in the header (next to the theme toggle) and a compact one
on the login page, so a language can be picked before signing in.
Neither renders on error pages, and the whole thing — dropdown and
route — disappears when only one locale is supported or
`locale_switcher=False` is set.

Each option is its own name, never translated ("English", "Français",
"Русский"); built-in names cover `en`, `fr`, `ru` and `en-XA`, and
`locale_names` names anything else, falling back to the code itself.

Choosing an option posts to `POST {base}/locale` (form field `locale`,
CSRF-protected like any other mutating route). A supported value sets
the `admin_locale` cookie (`path` = the admin mount, `samesite=lax`,
`httponly`, one year, `secure` when the request is HTTPS) and
redirects back to wherever the visitor was, validated against the
`Referer`; an unsupported value sets nothing but still redirects.

A host that must force one language — company policy, a
single-tenant deployment — combines `locale_switcher=False` with a
`locale_resolver` that always returns it.

## Translating your own strings

### Host catalogs

A `ModelAdmin`'s own text (labels, help text, action messages, ...)
isn't extracted into the framework's catalogs — it belongs in yours,
layered on top with `catalogs`:

```python
admin = Admin(model_admins=[...], catalogs=[("locales", "myapp")])
```

Each entry is a `(localedir, domain)` pair, the same shape
`gettext.translation` takes: a directory holding
`<locale>/LC_MESSAGES/<domain>.mo`. Build and refresh those with
`pybabel`, extracting from your own code and templates
(`babel.cfg` in this repo shows the `jinja2.ext.i18n` extraction
config to mirror):

```bash
pybabel extract -F babel.cfg -k N_ -o locales/myapp.pot .
pybabel init -i locales/myapp.pot -d locales -D myapp -l fr    # first time
pybabel update -i locales/myapp.pot -d locales -D myapp        # after that
pybabel compile -d locales -D myapp
```

Babel is a dev-time tool only — the compiled `.mo` files are what ship,
and `gettext` (which reads them) is in the standard library, so a host
using `catalogs` gains no new runtime dependency either. A later
`catalogs` entry overrides an earlier one (and the framework's own) for
the same message, so a host catalog can also reword the framework's
strings — see below.

### In templates

```jinja
{{ _("Save") }}
{{ _("%(label)s is required.", label=field.label) }}
{{ ngettext("%(num)d record", "%(num)d records", n) }}
x-text='dark ? {{ _("Light mode")|tojson }} : {{ _("Dark mode")|tojson }}'
```

- `_(message, **variables)` — translated, then `%`-formatted only when
  keyword arguments are given. Placeholders are Jinja newstyle
  (`%(name)s`), which also auto-escapes.
- `ngettext(singular, plural, n, **variables)` — `n` picks the plural
  form; `num` defaults to `n` if not given explicitly, so a count shown
  in the text usually needs no extra keyword, as in the `%(num)d
  record`/`%(num)d records` example above.
- `|tojson`, in a **single-quoted** attribute — `tojson` doesn't escape
  `"`, so a double-quoted attribute would break. A plain `{{ _(...) }}`
  inside a quoted JS string breaks on a French apostrophe (`Mode
  d'affichage`); the JSON string literal survives the attribute's HTML
  escaping instead. Inside a `<script>` block, where there's no
  attribute escaping to survive, `{{ _(...) }}` alone is fine — it's
  already a quoted JS string there.
- A host string goes through the same functions with a non-literal
  argument: `{{ _(field.label) }}`, `{{ _(fieldset.description) }}`.
- A whole sentence is one message — interpolate with a placeholder,
  never concatenate translated fragments: `{{ _("Remove this
  %(label)s?", label=_(inline.label)) }}`, not `{{ _("Remove this")
  }} {{ _(inline.label) }}?`.
- A literal `%` in a message needs no escaping when `_`/`ngettext` is
  called with no keyword arguments; it needs doubling (`%%`) only once
  the call takes arguments — `_()` here returns plain `str`, never
  `Markup`, so autoescape still escapes the translation at output the
  same as any other value.

### In code

```python
from polyadmin.i18n import N_, gettext, ngettext

gettext("%(name)s deleted.") % {"name": name}
ngettext("%(num)d record", "%(num)d records", n) % {"num": n}
N_("Broadcast sent.")  # marks a string for extraction without translating it yet
```

`get_locale()` reads the resolved locale directly, from a
`contextvars.ContextVar` the FastAPI adapter's route class sets for
the whole request — which is what lets an action handler or a
`ModelAdmin` method translate without taking a request parameter of
its own.

A string an action or validator returns is translated where the
framework uses it — an action's return value when it becomes a flash
message, a validator's `ValueError` when the form re-renders — so a
static message only needs a host catalog entry, while an interpolated
one is translated by your own code with `gettext`:

```python
def _valid_balance(value):
    if isinstance(value, str) and value != "":
        raise ValueError("Enter a valid number.")  # translated by the framework
```

Translating an already-translated string is harmless: it misses the
catalog (the text isn't the English message any more) and comes back
unchanged, so a validator is free to call `gettext` itself instead —
both styles compose.

## Rewording the framework's strings

Give a host catalog an entry keyed by the framework's own English
message, and it wins over the framework's translation for that locale
(the lookup order is: host catalog, then framework catalog, then the
English message itself) — an ordinary `msgid`/`msgstr` pair in your
own `.po` file, keyed on the framework's text:

```po
msgid "Delete selected"
msgstr "Remove checked items"
```

## Dates and numbers

Formatting happens in the browser, not on the server, so there's no
server-side locale-formatting dependency.

- Date and datetime fields render as
  `<time datetime="2024-03-01" data-format="date">2024-03-01</time>`
  (or `data-format="datetime"`); `DecimalField` values render as
  `<span data-format="decimal" data-value="19.9">19.9</span>`.
  Integers render as-is — they're commonly IDs, years, or codes, where
  `1 234` would be wrong. A `Decimal` value is shown exactly as given
  (`format(value, "f")` only changes notation, never precision); a
  float — what a `"decimal"` field's parsed form value becomes — is
  shown in the shortest fixed-point form that round-trips back to it,
  with no forced trailing zero.
- A shared inline script in `theme.html` formats every such element
  with `Intl.DateTimeFormat`/`Intl.NumberFormat`, keyed off
  `document.documentElement.lang`, on load and after every htmx swap.
- Date-only values are formatted from their year/month/day components,
  never through `new Date("YYYY-MM-DD")` (which parses as UTC midnight
  and shows the previous day west of Greenwich). A datetime carrying an
  offset shows in the browser's own timezone; a naive one shows as
  wall-clock time, unconverted.
- Form inputs (`<input type="date">`, etc.) keep native ISO values;
  exports stay machine-readable. Without JavaScript, the ISO value
  shows as-is.
- The date picker's weekday and month names come from `Intl` with the
  page's own `lang`, not the browser's ambient locale.

The framework does not itself validate a date or a decimal typed into
a form field — a host validator does that, as `_valid_founded_date` and
`_valid_balance` in `examples/fastapi/organization_admin.py` show.

## The pseudo-locale

`pseudo_locale=True` enables `en-XA`: not a catalog, but a wrapper
around the real translator. It translates as `en`, then accents the
letters and brackets the result — `Save` becomes `[Šàvé]` — leaving
`%`-placeholders intact so the string still formats correctly. Enable
it in development or CI only; it exists to make an untranslated string
visible by inspection — any text on the page that isn't bracketed and
accented went out without passing through the translator.

## Not supported

- **Right-to-left scripts.** `dir` is always `ltr`.
- **Server-side value formatting.** Dates and decimals are formatted
  in the browser (see above) — there's no server-side equivalent for a
  host that can't run JavaScript.
- **Translated URLs or slugs.** A resource's route is always its
  `slug`, in every locale.
